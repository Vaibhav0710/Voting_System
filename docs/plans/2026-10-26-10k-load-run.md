# 10k Load Run Implementation Plan

**Goal:** Measure how many votes per second the system sustains on the dev laptop, prove 10,000 votes at that rate meet p95 < 500 ms with 0 errors, and prove a 10,000-vote burst keeps vote integrity.

**Architecture:** Gatling simulations in `load-tests/` (standalone Maven module, runs against the compose stack through the
gateway). New pure helpers (status tally, load plan, integrity report) get JUnit tests; a post-run integrity check reads
the voting, chain and results APIs. Prometheus + Grafana and a small sampler script record why a run slowed down.

**Tech Stack:** Java 17, Gatling 3.11.5 Java DSL, JUnit 5.10.5 + AssertJ 3.25.3 (same versions as the services), Docker Compose, Prometheus 2.54.1, Grafana 11.2.2, PowerShell 5.1.

**Spec:** the Design section below (agreed with Vaibhav 2026-10-26).

**Progress (2026-10-26):** Tasks 1–5 committed and pushed (`mvn -f load-tests/pom.xml test` 15/15). Task 6 smoke run
passed after two environment findings (kind cluster competing for Docker; cold start of voting-service) and a
result-service fix (Kafka consumer metrics, committed and pushed 2026-10-27); see BLACKBOOK. 2026-10-27: a failed
integrity check now fails the run (17/17 helper tests); its HTML report is then rebuilt with `-Dgatling.reportsOnly`.
Next: Task 7. Changes against the text below, found while building:
- `ElectionReport.Mode` is `{ PACED, OVERLOAD }`, not `BURST`: the step test also pushes past capacity on purpose, so it
  and the burst both use the lenient mode (votes stored after a gateway timeout are reported, not failed).
- `VoteRun` (new) holds what each voting simulation shares (`prepare(long neededVoters)`, `election()`, `tally()`,
  `check(Mode)`), so the three simulations do not repeat their `before()` / `after()` code.
- `ElectionCheck` waits until the stored count has been steady for 5 s (a vote can commit after the gateway gave up on
  it) and retries reads that get 503 while a circuit breaker is open (`untilAvailable`, 3 more tests in `ElectionCheckTest`).
- Prometheus scrapes every 5 s instead of 15 s, so a 15 s level gets three samples.

## Design

### Decisions (2026-10-26)
| Question | Decision | Rejected |
|---|---|---|
| What "10,000 concurrent votes, p95 < 500 ms" means | **Paced 10k**: a step test finds the highest steady rate with p95 < 500 ms and 0 errors (the knee); 10,000 votes at 80 % of the knee must pass p95 < 500 ms and 0 errors. **Burst**: 10,000 votes at once, judged on integrity only. | Closed-model N in flight (arbitrary N); true burst must meet p95 (measures the laptop, not the design) |
| Tuning | Baseline first, then one change per round, at most 2 rounds, keep a change only if the knee improves ≥ 10 % | Tune everything up front (cannot show what helped) |
| Chain cost | One extra step test with `VOTING_CHAIN_ENABLED=false` | Chain on only |
| Monitoring | Prometheus + Grafana only, plus `docker stats` and Postgres lock-wait samples | Full observability profile (ELK/Zipkin take GBs of RAM); Gatling only |

### Facts the plan rests on
- Laptop: i5-9300H (4 cores / 8 threads), 15.8 GB RAM; WSL2 default gives Docker ~7.9 GB and all 8 threads. Gatling runs on the same machine.
- One election = one chain: every vote locks `election_chain_heads` (`SELECT … FOR UPDATE`) until commit.
- `VoteService.castVote` is one transaction; it most likely holds a DB connection through the Feign candidate check, and voting-service's pool is 10 (Hikari default). Confirm with `hikaricp_connections_pending`.
- Gateway: 5 s time limit per route; circuit breaker opens when ≥ 50 % of the last 20 calls fail and stays open 10 s. Every vote also calls user-service `/auth/validate` (JWT parse only, no DB).
- Seeding: register + login both run BCrypt. 2026-10-25: about 20 seed attempts failed with 503 at ~5 s, most likely because the kind cluster from the K8s test was running alongside (found in the smoke run); the run at 24 voters/s passed (20,016/20,016 OK, p95 213 ms). The auth route needs the `GATEWAY_AUTH_*` override for that (48 req/s > default 10/s).
- Voter JWTs live 24 h (`JWT_EXPIRATION`): seed on the run day. Each simulation creates a new election, so one seed serves every run that day.
- Postgres `max_connections` = 100; pools today: user 20 + candidate 10 + voting 10.

### Runs (Task 7), in order
| # | Run | Config | Pass |
|---|---|---|---|
| R1 | Seed 10,000 voters | auth override 60/120, `SEED_RATE=24` | 0 failed requests; voters file ≥ 10,000 tokens |
| R2 | Capacity, baseline | chain on, voting pool 10 | none (find the knee) |
| R3 | Paced 10k, baseline | chain on, voting pool 10, rate = 80 % of knee | p95 < 500 ms, 0 KO, INTEGRITY OK |
| R4 | Tuning rounds (0–2) | one change each (see table in Task 7) | knee +10 % or revert |
| R5 | Capacity, chain off | `VOTING_CHAIN_ENABLED=false`, best config | none (compare knees) |
| R6 | Burst 10k | chain on, best config | INTEGRITY OK |

### What is measured per run
Gatling: total, OK/KO, status breakdown, p50/p95/p99/max, throughput. Integrity (after each run): accepted (201s),
stored, stored after a gateway timeout, chain valid + broken links, tally total and per candidate, tally lag.
Resources: max voting pool pending/active, max Kafka consumer lag, max JVM CPU per service (Grafana), max container CPU
and max Postgres lock waits (sampler).

## Global Constraints
- All traffic goes through the gateway `http://localhost:8080`; no service ports are exposed for the test.
- Never log or print voter tokens or passwords; `load-tests/voters.csv` stays git-ignored.
- Load numbers are always stated with size and rate ("10,000 votes at 80 votes/s"), never as "concurrent" unless the burst run.
- Each task is committed only after Vaibhav has reviewed it.
- `P95_LIMIT_MS` stays 500.

## Review Focus
1. **Voters file shorter than the planned arrivals** → the queue feeder empties mid-run and Gatling stops with an unclear error. Expect a refusal before injection: "needs N voters, voters.csv has M". Pinned by `LoadPlanTest.refusesWhenVotersFileIsShort` (Task 1).
2. **Voter tokens older than 23 h** → every vote is 401 and looks like a load failure. Expect a refusal: "voters.csv is older than 23 h: re-seed first". Pinned by `LoadPlanTest.refusesStaleVotersFile` (Task 1).
3. **Request with no HTTP response** (connection reset, Gatling timeout) → there is no status to record. Expect it counted as `no-response`, never a crash. Pinned by `StatusTallyTest.countsMissingStatusAsNoResponse` (Task 1).
4. **Burst: gateway returns 503 after 5 s but the vote was stored** → stored > accepted. Expect it reported as "stored after timeout" in OVERLOAD mode and as a problem in PACED mode. Pinned by `ElectionReportTest.overloadReportsStoredAfterTimeout` and `pacedFlagsStoredAboveAccepted` (Task 2).
5. **Tally still catching up** when the check runs → false mismatch. Expect polling up to `TALLY_WAIT_SECONDS`, then a problem naming the gap. Pinned by `ElectionReportTest.flagsTallyBehindStore` (Task 2); polling itself checked in the smoke run (Task 6).
